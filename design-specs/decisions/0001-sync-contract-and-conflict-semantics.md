# ADR-0001: Define the sync wire contract with per-operation idempotency, tombstones, and a monotonic delta cursor

- **Status:** Accepted
- **Date:** 2026-09-05
- **Deciders:** Steven Waldren (accepted from implementation-planning recommendation)
- **Related:** SRS_v2 §3.6, §3.8, §4.5, §5.3, AC 13.1 · [ADR-0007](0007-packages-core-ownership.md) · `docs/sync-contract.md`

## Context

SRS_v2 §4.5 already settles the sync _architecture_: the mobile client writes locally first, appends to a local `sync_queue`, pushes in client-timestamp order, and the server resolves conflicts last-write-wins by timestamp, writing the losing version to the audit log rather than discarding it. §3.8 adds that every rule is re-enforced server-side on every synced operation, and that a queued operation rejected server-side is retained locally and surfaced for correction, never dropped. None of that is reopened here.

What the spec does not specify is the **wire format** — and every unspecified part of it is load-bearing. The sync engine is the hardest component in this system: offline queue ordering, replay after a failed batch, clock skew between a phone and the server, deletes propagating to a second device, and untrusted payloads arriving from a device that may have been offline for days all interact. Once mobile clients are in the field, the wire format is effectively frozen: a change requires a coordinated server and app-store release, and old app versions keep speaking the old contract in the meantime.

This decision was surfaced by implementation planning rather than by hitting the problem in code. It should be re-checked when the first two-device sync scenario is exercised at Gate C.

## Decision

We will define the sync contract in `docs/sync-contract.md` and its types in `packages/core/src/sync/`, merged **before any sync code is written**, with these semantics:

1. **Idempotency is keyed on a per-operation UUID**, generated by the client when the operation is enqueued — not on the entity UUID.
2. **A push batch returns per-operation results**, each `accepted` or `rejected` with a machine-readable reason code and the offending field. A batch never fails as a unit.
3. **Deletes are tombstones**, not row removal.
4. **The delta cursor is a server-assigned monotonic sequence number**, not an `updated_at` timestamp.
5. **The clock-skew allowance is an admin-managed threshold** in the §3.11 configuration tables, with a stated default — not a constant in code.
6. **Operations within a batch are applied in strict client-timestamp order**, and the server does not reorder them.

## Consequences

**What this gets us.** Replay safety is exact: a client that pushes, loses its connection before reading the response, and pushes again produces no duplicate rows, because the per-operation UUID identifies that specific write attempt. A single malformed row cannot block a patient's backlog. A delete made on a phone reaches a second device. The cursor cannot silently skip rows. And the skew allowance can be tuned clinically without a deploy, consistent with the §3.8 rule that thresholds are configuration.

**What this costs.** Tombstones mean `observations` and every other synced table accumulate rows that are logically deleted but physically present, so every read path must filter them and the eventual purge policy is now coupled to the PHI retention period — which is still blocked on counsel. Per-operation results make the client's queue processor more complex than a batch-level success flag: it must reconcile a partially-applied batch. The monotonic sequence requires a server-side sequence column with an index, and it must be assigned inside the same transaction as the write or the cursor can hand out a value whose row is not yet visible.

**What it forecloses.** Choosing the entity UUID as the idempotency key later becomes impossible without a migration, because it cannot distinguish a replayed create from a legitimate later update of the same row — the failure would show up as silently lost edits, not as an error. Moving from tombstones to hard deletes is likewise a one-way door, since the audit requirement in §3.6 depends on the deletion being recoverable. We would find out at Gate C, when two devices first diverge.

## Alternatives considered

| Alternative                             | Why not                                                                                                                                                                                                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Entity UUID as the idempotency key      | Cannot distinguish a replayed create from a legitimate later update of the same row. The failure mode is a silently dropped edit, which is the exact outcome §5.3 forbids.                                                                                               |
| All-or-nothing batch application        | One implausible row — precisely the kind Tier 2 exists to let through — would block every subsequent entry a patient made while offline. That is the data-loss shape §5.3 forbids, arriving through the back door.                                                       |
| Hard deletes                            | A hard delete cannot propagate through a delta cursor to a second device; the row simply stops appearing, which the second device cannot distinguish from "not yet synced." §3.6 requires the deletion be auditable regardless.                                          |
| `updated_at` timestamp cursor           | Loses rows written inside the same millisecond, and breaks outright on any server clock adjustment (NTP correction, DST-unaware code, leap second). The loss is silent.                                                                                                  |
| Clock-skew allowance as a code constant | Directly contradicts the §3.8 rule that all numeric bounds are admin-managed configuration. Someone will propose it again because it feels like an engineering constant rather than a clinical one — it is neither; it is a device-fleet property that will need tuning. |
| Server-side reordering of a batch       | Last-write-wins resolution is defined by client timestamp, so reordering changes which version wins. The server must not silently alter the outcome.                                                                                                                     |

## Spec impact

**No spec change.** This decision fills a gap below the level SRS_v2 §4.5 describes; it does not contradict anything the spec states. `docs/sync-contract.md` becomes the normative reference for the wire format and is listed in the implementation plan as a required handoff artifact before P2.S1b.

## Compliance and safety review

Touches PHI handling and audit logging directly. Two requirements carry forward into implementation and must be verified by `hipaa-compliance-reviewer` at P2.S1:

- Every sync-applied write, **and every conflict loser**, routes through the same `AuditContext` as a direct write. These are the two paths that get missed when audit logging is added per-handler rather than structurally.
- Rejection reasons returned to the client are field identifiers and rule codes only. They must never echo the offending clinical value, because rejection responses are logged on the client.

## Notes

Open: the tombstone purge policy, which cannot be settled until the PHI retention period comes back from counsel. Until then tombstones are retained indefinitely.

Re-check this ADR at Gate C, when two-device sync and preference propagation first exercise the contract under real conditions.
