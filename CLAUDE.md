# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

**`apps/api`, `apps/web`, `apps/mobile`, `packages/core`, `packages/seed`, `packages/ui` and `packages/config` all exist as code. There is no `apps/admin`.** `apps/api` is scaffolded (P1.S1) with its schema core (P1.S3), audit and threshold services (P1.S5), first PHI endpoints (P2.S1a) and sync (P2.S1b); `packages/core` has its kernel (P1.S4), sync wire contract (P2.S0) and generated API client (P2.S1a); `apps/web` and `packages/ui` landed at P2.S3; `apps/mobile` landed at P2.S2a. `apps/api` has typed/validated config, the structurally separate patient/admin OIDC guards, a liveness health check, OpenAPI generation, and a structured Pino logger whose serializers never assemble a request/response body into a log line, backed by a credential-redaction list (not a "PHI-scrubbing" filter — no PHI payload is ever logged in the first place, so there is nothing for one to scrub) — plus a Prisma schema, migrations, and a `PrismaService`/`PrismaModule` wired into `AppModule` (P1.S3; see `design-specs/data-model/p1-s3-schema-coverage.md`).

Audit logging exists and is real (P1.S5): a **global** `AuditInterceptor`, an `@Audited()` decorator, and `route-guard-coverage.spec.ts`, which fails the build if any mutating route carries no `@Audited()`. `POST`/`GET /api/v1/observations` (stoma output only) is the first business-logic surface (P2.S1a) — it writes the observation and its audit row **in one transaction**, and is the shape every later PHI write path should copy rather than re-derive.

**Sync exists (P2.S1b):** `POST /api/v1/sync/push` and `GET /api/v1/sync/delta`, in `apps/api/src/sync/`. `docs/sync-contract.md` is normative and governs — where it and the code disagree, the code is wrong. Three things about it are easy to undo by accident and are covered in that module's own comments: a **data** error fails one operation with a `rejected` result inside a `200` while a **protocol** error fails the whole request with a code and nothing else (§6.1/§6.2); payload *content* is validated per operation and never by a whole-body validator over the operations array, which is how "a batch never fails as a unit" turns back into all-or-nothing batching; and the delta query withholds the in-flight transaction window (ADR-0013) because a plain `ORDER BY server_sequence` silently and permanently hides rows from a device.

See `apps/api/README.md`.

**The two clients exist. `apps/mobile` has the four clinical entry screens; `apps/web` still has none — it reads.**

`apps/web` (P2.S3) is the online-only React + Vite SPA: OIDC Authorization Code + PKCE, and one view of a patient-local day — the stoma output chart and accessible table, **Daily Net Fluid Balance** (P3.S1b) computed from canonical values and rounded once (ADR-0005), and **urine output** beside it (P3.S2). The two figures are adjacent and never combined: urine is excluded from the balance on purpose (SRS §3.7), and both blocks say so, because a reader who assumes otherwise reads a reassuring balance while urine output may be dangerously low. The exclusion is enforced once, by LOINC code in `packages/core/src/hydration` — the page hands the balance every observation of the day undifferentiated rather than pre-filtering, so there is no second place it can be forgotten. Urine is also the one signal whose entries may have **no volume** (AC 12.1 AC2), so its block reports the measured total *and how much of the day that covers*, and a day recorded only by colour says so instead of rendering `0 mL` — an invented reading, in the most alarming possible direction for this signal. A day missing one side still shows the figure but says it is not a complete balance — output with no intake logged produces a large negative number that reads as a severe deficit when it may only be an unlogged one. The page groups by the **patient's local day** (ADR-0016): it fetches a window wider than the day and selects client-side, because a local day straddles two UTC days for most patients. It renders the **signed-in account's own** records: `GET /api/v1/observations` takes no patient identifier anywhere, so there is no physician identity and no patient-selection path, and the copy deliberately claims neither. SRS §3.5 Epic 5's share link is the intended route for a physician reader and does not exist yet.

`apps/mobile` (P2.S2a, P2.S2b, P3.S1, P3.S2) is the offline-first patient app: local SQLite, OIDC + biometric auth, the Add Output / Add Intake / Add Meal / Add Urine screens, the background sync worker, and the correction inbox. **Add Urine is the only entry screen where the amount is optional** (SRS §3.7, AC 12.1 AC2): a patient who cannot measure saves a colour alone, which is the first and so far only observation this system stores with no `valueQuantity`. `apps/mobile/src/entry/useVoidedUrineEntry.ts` picks the validation engine from what was entered, so no screen decides which rules stop applying. Being the one place PHI rests on hardware outside the covered entity's control, it carries device-side controls the server's protections do not reach: the local store is SQLCipher-encrypted (ADR-0014) and bound to one OIDC subject, so a different patient signing in destroys it — without that, the next person on a shared phone reads the previous patient's diary, and their queued rows push under the new identity, putting a **false author on an immutable audit row**. Biometric unlock stays fully offline, but an enrolment change invalidates the stored refresh token (ADR-0015). **Sign-in is completed by `app/redirect.tsx`, not by the hook that starts it** (ADR-0021): on Android the OIDC redirect is resolved to `MainActivity` — the only component owning the `ostomydiary` BROWSABLE filter — and `singleTask` brings its task to the front, so `promptAsync()` never reports the success `expo-auth-session` is waiting for and sign-in could not complete at all (#72). The code arrives in the deep link instead, and the redirect route reads it, verifies `state`, and exchanges. `useOidcLogin().login()` therefore returns a launch outcome, never tokens, and the in-flight PKCE verifier is kept in SecureStore **without** `requireAuthentication` — a deliberate narrowing of ADR-0015, since it is read while the session is being established. **v1 ships this client on Android only** (ADR-0020) — iOS was never built, so the controls above had never compiled on it, and ADR-0014's open iCloud-backup gap is closed by that scope rather than by a plugin. Sign-out still purges everything, but it now **warns with a count first** when entries are unsent, which is the gap P2.S2a recorded.

`apps/mobile/src/sync/` is the worker (P2.S2b). `docs/sync-contract.md` governs it and every module cites it by section; read that document before changing any of them. Three things there are easy to undo by accident: the push batch is **split at each clock-correction discontinuity** (§3.2) without which one NTP correction strands a patient's whole backlog behind a `400` nothing may retry; a `5xx`, a network failure and an **undecodable result** all mean *unknown fate* and go back on the queue, never to the correction inbox (§9.3); and the delta cursor advances **only** from a delta response (§3.6/§9.4). A §6.1 protocol error that survives isolation down to one operation is quarantined so the rest of the queue drains — see `markQuarantined` for why that reuses the `rejected` status rather than adding a fourth.

**The generated API client cannot express the sync contract's discriminated unions** — OpenAPI flattens them, so `@ostomy/core/api-client`'s `SyncOperationResult` has every union member optional. `apps/mobile/src/sync/responseDecoding.ts` is the decode boundary that restores the invariants; never consume those generated sync types directly.

**None of the mobile device-side controls are verified on hardware.** jest runs no keychain and cannot simulate biometric enrolment invalidation, so a green `pnpm verify` proves nothing about them. The same caveat covers the entry screen's rendering: the logic is unit-tested, but nothing in CI runs it on a device or a simulator. `docs/gate-b-hardware-verification.md` enumerates the steps that would close this (HW-1 to HW-10) and records which have been run — none yet. An emulator pass never closes one, so do not edit this sentence on the strength of one.

`packages/ui` (P2.S3) holds the shared accessible primitives and design tokens both SPAs build on. Its tokens are asserted against `styles.css` by a completeness test, and its contrast ratios are computed rather than claimed — every hand-written ratio in the first version was wrong, all understated.


**`apps/web`'s typecheck runs `tsc -b --noEmit --force`, and the `--force` is load-bearing.** It is the only workspace using `tsc -b`, and its project has no reference to `packages/core` or `packages/ui` — it resolves them through `node_modules`. So `tsc -b`'s up-to-date check compares only that app's own sources against `tsconfig.app.tsbuildinfo`, and a `packages/core` rebuild that changes a published type leaves the cache looking current. P3.S2 hit it: `Observation.valueQuantity` became optional, three call sites in `formatObservationsForDisplay.ts` stopped compiling, and **`pnpm verify` reported green** until the tsbuildinfo was deleted by hand. A verify step that can pass on code which does not compile is worse than no step. Don't "optimise" the flag away.

**The integration suite skips itself when Docker is unreachable, rather than failing.** Ownership authorization, audit coverage, the append-only grant check and the no-PHI-in-logs assertions all live there, so a green `pnpm verify` on a machine with no Docker daemon has proven much less than it looks like. Start Docker before trusting it.

`packages/core` is an ESM package with six owned subpaths (ADR-0007) and no root `"."` export: `src/units` (canonical mL/kg types and conversion, mixed-system values unrepresentable in the type, ADR-0004/ADR-0005), `src/validation` (the two-tier engine — Tier 1 hard-blocks, Tier 2 warns via a return type structurally incapable of blocking — with thresholds injected, never hardcoded, and `ESTIMATION_METHOD_CODE` resolved at ADR-0018 and still a discriminated union, not `string | null` — the shape is what the next unresolved terminology code should copy), `src/hydration` (the Daily Net Fluid Balance LOINC classification, voided urine excluded on purpose per §3.7 — nothing beyond that; the composite status is P6/P7), and `src/i18n` (the shared English catalog plus `Intl` formatters). Its namespaces are `common`, `validationErrors`, `validationWarnings`, `redFlags` and `clinicalCaveats` — shared, and where anything with clinical meaning must live — plus `mobile` and `web`, which are **scoped by app, not by audience** and may hold only shell copy with no clinical meaning. ADR-0006's "no per-app catalogs" rule is satisfied by keeping every namespace in this one package: a reviewer auditing patient-facing text reads all of it in one place, which is the rule's actual argument. Nothing is duplicated between `mobile` and `web`. `apps/api` depends on it and `pnpm verify`'s `verify:core-require` step proves the CommonJS API can `require()` its built ESM output (ADR-0010). `src/sync` (P2.S0) holds the wire contract types for `docs/sync-contract.md` — that document governs, and the types are corrected to match it, never the reverse. Build outbound wire objects with the constructors it exports (`syncRejectedResult`, `syncDeltaTombstone`, ...), never by spreading a database row or a validation result into a literal: TypeScript's excess-property check does not apply to spread properties, so a spread typechecks cleanly and ships a deleted entry's clinical values or a rejection's offending value. `src/api-client` (P2.S1a) is the typed client, **generated** from `apps/api/openapi.json` by `pnpm --filter @ostomy/api api-client:generate` and never hand-edited — if it is wrong, fix the zod schemas next to the handlers and regenerate. `src/fhir` is not built yet (owned by `fhir-data-modeler`). See `packages/core/README.md`.

**Seed data exists (P2.S4).** `packages/seed` generates scenarios deterministically and validates every row against `packages/core` *before* anything writes it (ADR-0009); `apps/api/src/seed/run.ts` is the Prisma writer, and `scripts/dev-reset.sh` invokes it. Only `stable-ileostomy` so far. Two things about it are load-bearing: seeded rows carry **no audit events**, because the seeder bypasses the API — a test asserting audit coverage must create its data through the API instead — and the generator is a **devDependency** of `apps/api`, which is what keeps it out of the `--prod` runtime image. `ALLOW_SYNTHETIC_SEED=true` is required to run it; that is a guard against a mistyped command, not a security boundary.

**`validation_thresholds` is seeded by a migration, not by `packages/seed`.** The rows are configuration every environment needs, not development data — `ThresholdsService` throws without them, and that sits on the Tier 1/Tier 2 path of every observation write and every synced operation, so a dev-only seed would leave production 500ing on its first clinical write. `ON CONFLICT DO NOTHING`, so a redeploy never resets a value an admin tuned. Integration tests upsert their own values over the defaults.

**The toolchain does exist** (sprint P0). `packages/config` holds the shared tsconfig, ESLint flat config and Prettier config that every workspace extends, and the root has working commands:

```
pnpm install
pnpm verify    # check:env + format + build:deps + lint + typecheck + test
               # + verify:build-artifact + verify:core-require + verify:api-client
               # — exactly what CI runs, in one step so the two cannot drift
```

plus `lint`, `lint:fix`, `typecheck`, `test`, `test:unit`, `format`, `format:write`, `check:env`. `docs/getting-started.md` is authoritative; use those commands rather than inventing any. When an app is scaffolded, record its real commands there and update this file.

Three lint rules fail the build rather than warn, because each backs a constraint that would otherwise depend on memory: the AGPL header, the admin/patient import boundary, and no hardcoded user-facing strings in UI directories. They have tests in `packages/config/eslint/__tests__/` — extend those when you touch a rule; two of the three shipped broken the first time precisely because they had none.

There is now a great deal of code and several load-bearing conventions enforced only by review, so filling it in is overdue rather than merely expected (issue #51). `docs/getting-started.md`'s app sections are written.

## The source of truth: SRS_v2.md

`design-specs/requirements/SRS_v2.md` (currently v2.6) is the single authoritative spec. It is self-contained and supersedes `Ostomy_App_Specification_v1.pdf` (historical reference only — do not consult the PDF to answer architecture questions). All six spec phases — user functionality, non-functional requirements, technical architecture, v1 scope additions, weight tracking & composite hydration status, and resting heart rate & signal concordance — are approved, the most recent on 2026-09-05. **v1 ships the mobile client on Android only** (ADR-0020, v2.6) — iOS is deferred, not dropped, and the browser SPA is the route for patients on other platforms.

**When a spec phase is approved, update this file in the same change.** A stale pointer here is worse than no pointer, because sessions read it and trust it. Check three things: the version number above, the phase list, and any rule below that the new phase changes.

**v1 covers colostomy and ileostomy only.** Urostomy was deliberately cut in Phase 4 (Appendix A) because a urostomy's stoma output *is* urine, making it a different data model rather than a third enum value. Do not reintroduce it as an ostomy type.

Read it before making architectural or data-model decisions. Section 4 in particular contains decisions that are already made, not open questions.

## Decisions made since the spec: design-specs/decisions/

Architecture decision records live in `design-specs/decisions/`, indexed in its README. **An accepted ADR can supersede SRS_v2.md** — check the index before treating a spec statement as final, and read any ADR touching the area you are working in.

Twenty-one are accepted (ADR-0001 to ADR-0021), covering the sync wire contract, testing strategy, monorepo tooling, canonical units, entry precision, i18n, `packages/core` ownership, admin API sequencing, seed data, the API's CommonJS module system, database roles and audit immutability, entered-measurement-system provenance, the delta cursor's visibility mechanism, on-device PHI encryption and ownership, biometric local access, the patient-local day boundary, PHI retention/deletion, the Measured/Estimated SNOMED qualifiers, the client clock-skew allowance, the Android-only v1 platform scope, and where the OIDC code exchange happens. ADR-0001 (sync) and ADR-0007 (`packages/core` ownership) bind almost every sprint — read both before writing shared or sync code.

Record significant new decisions there using `0000-template.md`: choices that are expensive to reverse, that a future contributor would otherwise re-litigate, or that look arbitrary without their context. Routine implementation choices belong in the code, not an ADR. An ADR that changes something the spec states must update the spec — and this file, where it changes a rule below — in the same change, or the repo ends up with two answers to the same question.

## Architecture decisions already locked in

From SRS_v2 Section 4 — treat these as settled unless the user reopens them:

- **Monorepo** via pnpm workspaces (`apps/*`, `packages/*`). TypeScript throughout, including infrastructure. No task runner — plain pnpm scripts (ADR-0003). `packages/config` is the shared build/lint/format base every workspace extends.
- **Module systems differ by workspace.** The repo is ESM (`"type": "module"`); `apps/api` is **CommonJS** with `nodenext` resolution, because NestJS's decorator DI does not fit the ESM defaults (ADR-0010). Consequence you must respect: the API's CJS build relies on Node's `require(esm)`, which throws `ERR_REQUIRE_ASYNC_MODULE` on **top-level await** — so `packages/core`'s entry graph must never use it. Vitest transforms to ESM and will not catch this; only running the built API will.
- **Mobile (`apps/mobile`)**: Expo managed workflow + React Native, **Android only in v1** (ADR-0020; iOS deferred, and the `ios` block in `app.json` is retained but inert). The *only* offline-capable client — writes to local `expo-sqlite` first, appends to a local `sync_queue` table, pushes to the API on connectivity restore.
- **Web (`apps/web`)**: React + Vite SPA, **online-only** by explicit decision. No local persistence layer. Don't add offline support to web.
- **Admin console**: a *separate* internal React/Vite SPA with **zero PHI access**, managing value sets, clinical default ranges, and validation thresholds. Backed by its own Cognito user pool, disjoint from the patient pool, so the boundary is enforced at the identity layer rather than by authorization logic. It consumes an isolated `/api/v1/admin/...` surface and must never import patient data types. Not yet scaffolded — there is no `apps/admin` directory.
- **API (`apps/api`)**: Node.js + TypeScript, NestJS recommended (module/guard/interceptor patterns map onto RBAC, audit logging, and validation — the compliance requirements make this a deliberate choice over Express/Fastify). REST, not GraphQL, versioned as `/api/v1/...`. Prisma against PostgreSQL.
- **Database**: PostgreSQL with a **FHIR-shaped relational schema** — not a FHIR-native store. Clinical tables map their columns 1:1 to FHIR R4 fields; FHIR `Bundle` resources are assembled on demand by a dedicated export module.
- **Infrastructure**: AWS — Fargate/ECS for the API, RDS PostgreSQL Multi-AZ, S3 (SSE-KMS, presigned URLs) for photos and PDF exports, S3+CloudFront for the web build, Cognito as the OAuth2/OIDC IdP, Secrets Manager + KMS. IaC in AWS CDK (TypeScript). CI/CD via GitHub Actions: `pr.yml` (lint, typecheck, test, dependency scan, and container images **built and run**) and `deploy-dev.yml` (the self-hosted runner). No AWS pipeline yet — that is P9.
- **Conflict resolution**: last-write-wins by **client timestamp**, applied server-side; the losing version is written to the audit log rather than discarded. Implemented at P2.S1b — `docs/sync-contract.md` §4 is the specification, and note that a create against an existing same-patient row is an ordinary last-write-wins comparison, **not** a rejection: rejecting it puts a correct entry in the correction inbox describing a problem the patient cannot fix.

## Data model rules that are easy to get wrong

- Output/intake logs are FHIR R4 `Observation`. Persist and transmit using FHIR-standard field names (`resourceType: "Observation"`, `valueQuantity.value`, `effectiveDateTime`) — not a custom schema mapped later.
- The mandatory **"Measured vs. Estimated"** toggle on every volumetric entry is stored as `Observation.method`, and **both answers carry an explicit SNOMED qualifier**: `414135002` |Estimated| and `258104002` |Measured| (ADR-0018, amended). `packages/core`'s `ESTIMATION_METHOD_CODE` and `MEASURED_METHOD_CODE` are the single place those values live — `apps/api` reads the constants, never a copy. **Changing either is a data migration, not an edit**: written rows keep the old code and nothing detects the disagreement until FHIR export. `method: null` at rest now means exactly one thing — "this observation has no toggle", i.e. weight or resting heart rate. It is still *accepted* on the wire as measured, because §8 requires understanding a client built before the amendment, and normalised before storage so no row records the ambiguity.
- Medications are a **separate** `medication_administrations` table (FHIR `MedicationAdministration`), keyed by RxNorm RXCUIs — not rows in the observations table. UI shows patient-friendly terms; the backend maps them to RXCUIs.
- App-native entities (appliance changes, leak events, peristomal skin condition, reminders, Quick-Add templates) have no FHIR equivalent and are ordinary relational tables. This asymmetry is the accepted trade-off of the Postgres-over-FHIR-native decision.
- Body weight also shares the `observations` table (LOINC 29463-7), with `method` left unpopulated — the Measured/Estimated toggle applies to volumetric entries only, since a weight is read off a scale. Observation codes are LOINC; SNOMED CT is used only for the `method` attribute.
- There are **four hydration signals**: net fluid balance, urine output, weight change, and resting heart rate. The patient dashboard shows one composite status with drill-down, escalating when two or more signals agree; the physician view keeps all four separate and uncombined. Don't combine them in the physician view, and don't show four bare numbers to the patient.
- Resting heart rate (LOINC 8867-4) stores measurement source and a resting-conditions flag as coded components; readings failing the resting check are saved and shown but **excluded from baseline computation**. An orthostatic pair is two linked observations with the postural rise derived, not stored.
- The heart-rate **red-flag threshold is a safety response, not validation**. The entry saves normally with no data-quality warning, and a separate prompt advises seeking care. Never route it through the validation warning path — that teaches patients to dismiss it. It is also the one threshold that is not patient-adjustable.
- Voided urine shares the `observations` table with other volumetric entries, distinguished by observation code — it is not a separate table. It is **excluded from Daily Net Fluid Balance on purpose**: net balance measures stoma losses, while urine output independently signals renal perfusion, and merging them would let a normal-looking balance hide a dangerously low urine output. Don't "fix" this by summing them.
- **Voided urine is the one observation that may carry no volume** (P3.S2, SRS §3.7, AC 12.1 AC2): a patient who cannot measure records a colour instead, and that entry is retained as a valid hydration observation. `observations.value_quantity_value` and `.value_quantity_unit` are therefore nullable, with four CHECK constraints keeping that from becoming a hole — the volume and its unit travel together, only code `9187-6` may omit the volume and only when `urine_color_code` is present, a colour belongs to no other code, and `method` requires a volume to qualify. **A missing volume is never zero.** `SUM()` skips NULL and application code that reads a missing value as 0 does not, and the two disagree forever afterwards, so the wire **omits** `valueQuantity` rather than sending `null` or `0` (`docs/sync-contract.md` §7.2). `packages/core`'s `validateVolumelessObservation` is the rule set for it — a separate entry point, not a flag, so no caller has to know which rules stop applying. The colour is an **app-native** value set (`urine_color`): there is no agreed code system URI for a pale-to-dark hydration chart, and until one is decided the FHIR export module must not emit it as a coded component.
- **Both write paths persist every field, and a test compares them.** `POST /api/v1/observations` and `POST /api/v1/sync/push` write the same entity through separate code, and both name each column explicitly. The cost of that discipline is that omitting an optional field typechecks cleanly: `fluidTypeCode` was missing from the sync push and from the delta payload from P3.S1 until P3.S2 found it, so every intake entry logged **offline** lost its categorisation while the identical payload through the direct endpoint kept it. When you add a payload field, add it to `sync.integration.spec.ts`'s "the coded fields survive a delta pull" block **first** — that test is what finds the sites, and there are more of them than anyone remembers: the two service write paths, `toObservationResource`, the delta emitter, `deltaPull.ts`'s INSERT **and** UPDATE, `toAuditSnapshot`, `incomingSnapshot` (the §4.1 conflict loser), `offlineWrites.ts`, and `corrections.tsx`'s re-enqueue. P3.S2 shipped an enumeration of four of those and every field-drop its review then found was at one of the others, so treat any list here as a starting point rather than a checklist (#68).
- Value-set members are **retired, never deleted**. Clinical records reference them by stable code, so a retired value must still resolve when rendering history. No admin action may change what a past entry means. A retirement is expressed by **absence** from `GET /api/v1/value-sets`, never by a flag — which is why `apps/mobile`'s cache does a delete-then-insert per set rather than an upsert (P3.S1): an upsert leaves a retired member on the device forever with nothing detecting the drift. Codes come from that cache; the *labels* are i18n catalog keys (ADR-0006), so a member an admin adds after a release ships has no copy and renders as "Another option" — a reachable state, not a defensive one.
- A patient's effective range is stored with its provenance — physician-set, patient-set, patient-confirmed suggestion, or clinical default, in that precedence order. An unconfirmed suggestion is never an active anomaly threshold.

## Validation

Two tiers, defined once in `packages/core`: hard block for structurally impossible input (negative volumes, future timestamps beyond clock skew, dates before the surgery date, missing Measured/Estimated), soft overridable warning for implausible-but-real values (the >2,000 mL rule is an instance of this class, not a special case). A warning must never become a block — a real 2,500 mL day is the data point the care team most needs.

Client-side validation, including offline on mobile, is a UX affordance only. Every rule is re-enforced server-side on write **and on every synced operation** — a payload from an offline device is untrusted input. A queued operation rejected server-side is retained locally and surfaced for correction, never dropped.

Numeric thresholds are admin-managed configuration, not constants in code. **`GET /api/v1/thresholds` (P2.S2b) is how a client gets them** — patient-guarded, no PHI, no audit row. `apps/mobile` caches the response in `validation_thresholds_cache` so it can keep validating offline, and that table is deliberately **unseeded**: a default there is a hardcoded threshold wearing a database costume, so an unfetched cache blocks the save rather than validating against invented numbers.

`packages/core`'s `MAX_REPRESENTABLE_VALUE_ML` / `MAX_VALUE_DECIMAL_PLACES` are *not* thresholds — they are the canonical column's shape (`DECIMAL(12,4)`). A client converting an imperial entry **must round to that scale**: `ozToMl(80)` is `2365.882365`, and un-rounded it trips Tier 1's precision rule, so every imperial entry is blocked with a message about decimal places the patient never typed.

## Non-negotiable constraints

These come from the spec and apply to every feature, not just "compliance work":

- **The governing rule is the FTC Health Breach Notification Rule, not HIPAA.** This product is direct-to-patient, so it is neither a covered entity nor a business associate (ADR-0017, `docs/compliance/breach-notification.md`). We build to HIPAA's *technical* safeguards anyway, as a voluntary standard — every rule below stands. What changes is which breach clock applies and that no BAA is legally required. It changes back the moment a provider offers the app to their patients, the likely route being SRS §3.5 Epic 5's share link.
- **Never log PHI.** Every PHI create/edit/delete is audit-logged with user identity, timestamp, and before/after values, to an append-only store separate from application logs. Those before/after values are clinical values, which is why ADR-0017 has to purge audit rows on account deletion.
- **A "day" is the patient's local day at the moment of entry** (ADR-0016), captured from the device and stored per observation as an IANA zone plus a derived `local_date`, never re-derived from a mutable profile or from the reader's timezone. Daily totals group by it. The stored instant remains the source of truth for ordering and sync; `local_date` is a grouping key only, and is not monotonic with the instant for a patient who crosses timezones.
- **PHI is retained for the account's lifetime.** A deletion request revokes access immediately and hard-purges within 30 days, **including that patient's audit rows**, via a privileged job that runs as the owner role and is unreachable from request handling (ADR-0017). This narrows ADR-0011: the guarantee is "no request handler can delete an audit row", not "nothing can". Never describe the audit log as strictly immutable without that qualification.
- **The API never runs as the database schema owner.** Two non-superuser roles: a migration/owner role for `migrate`, and a runtime role for request handling that holds `SELECT`/`INSERT` on `audit_events` and **no `UPDATE`/`DELETE`** (ADR-0011). Append-only is enforced by grant, not by convention — a superuser or table owner bypasses it and makes the P1.S5 audit test pass while proving nothing. Role and grant changes go in a **migration**, never only in a Compose init script: Testcontainers starts its own PostgreSQL and never sees one.
- **No real PHI outside production.** Dev and staging use synthetic or de-identified data.
- **Accessibility is a hard target, not polish**: WCAG 2.1 AA across both clients. The patient population skews older and post-surgical — screen-reader support, scalable text, and touch-target sizes are requirements.
- **No hardcoded user-facing strings.** v1 ships English-only, but all copy must be externalized and date/time/number/unit formatting must be locale-aware from day one. Patient-facing copy targets a 6th–8th grade reading level.
- **Units**: a single metric/imperial preference governs both volume and weight (mL+kg or oz+lb). Mixed-system combinations must be impossible to select — make them unrepresentable in the type, not merely unselectable in the UI. All logging and display respect it; stored canonical values are never rewritten when it changes. **Canonical storage is always mL and kg** regardless of preference; imperial is a render-time conversion only (ADR-0004).
- **Every observation write must supply the entered measurement system.** `observations.entered_measurement_system` is `NOT NULL` with no default (ADR-0012), and is the **client's asserted entry system** — not the server's current profile (`docs/sync-contract.md` §7.2; ADR-0012 amended at P2.S1a). The server validates only that it is `metric` or `imperial`. For a queued offline write only the device knows what the patient typed in, so re-deriving it server-side is wrong precisely for the patients who switched, and refusing on a mismatch rejects on a field no entry form contains. It is what makes ADR-0005's conversion rounding implementable, and it is permanent per row: no later migration can recover the truth if it is stored wrongly.
- **Precision**: volume fields accept positive decimals, not integers. Tier 1 rejects negatives, **zero**, non-numeric input, and — since P2.S1a — anything the canonical `DECIMAL(12,4)` column cannot hold: a magnitude at or beyond `10^8`, or more than 4 decimal places. Those two were previously HTTP 500s, which `docs/sync-contract.md` §9 tells a client to re-push indefinitely, so a mistyped volume retried forever instead of reaching the correction inbox. Stored values keep their entered precision. A volume *converted* between measurement systems is rounded to the nearest whole unit for display only — but **weight is excluded from that rule** and shows one decimal place in both systems, because rounding a converted weight to a whole unit would discard exactly the day-over-day changes the weight signal exists to detect (ADR-0005, SRS AC 2.1 AC 4).
- **Daily totals are computed from canonical values and rounded once, never summed from rounded per-entry display figures.** Daily Net Fluid Balance is one of the four hydration signals; accumulated display rounding across a day of entries is a clinical-accuracy defect (ADR-0005).

## Development environment

Development does **not** run on AWS. It is a single shared Docker Compose stack on an on-premise Ubuntu LTS server: API, PostgreSQL, MinIO in place of S3, a mock OIDC provider in place of Cognito, both SPAs as static builds. LAN-only, plain HTTP, synthetic data only. Deployed by a self-hosted GitHub Actions runner (outbound-only, so no inbound firewall rule). Database persists across deploys; migrations run automatically; `dev-reset` wipes and reseeds. Full methodology in `docs/deployment-development.md`.

Two rules this imposes on application code:

- **Never import a Cognito SDK into request handling.** The API takes a standard OIDC issuer, JWKS URI, audience, and claim mapping as configuration. Cognito-specific behavior goes behind a provider adapter.
- **Never assume AWS-hosted S3.** Endpoint, region, credentials, and path-style addressing are configuration. MinIO requires path-style, so virtual-host-style URL assumptions break development outright.

Push delivery sits behind the same kind of adapter (Expo in production, log-only in development).

Nothing on this host may ever hold real PHI or a production credential — not temporarily, not to reproduce a bug. The runner's `docker` group membership means a host compromise is total, and the only defense that holds is that there is nothing valuable there.

Staging is the parity gate. Fargate orchestration, TLS, real Cognito, and KMS are untested until staging exists; `docs/deployment-development.md` lists the deferred risks that staging must cover.
