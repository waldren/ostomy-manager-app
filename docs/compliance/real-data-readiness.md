# Real-data readiness

- **Owner:** [Security & Privacy Officer — TBD]
- **Decided by:** [ADR-0022](../../design-specs/decisions/0022-self-hosted-production-on-one-host.md)
- **Status:** **not ready.** No item is signed off.

These are the things that must be true before any server is initialised to hold a real patient's data.

**The deploy CLI reads this file**, from inside the signed release tag being deployed (ADR-0022 item 3), never from a working copy. `init --classification real` refuses unless every row in the table below has a sign-off (D.S1 slice 3). This list is a gate the tooling enforces, not one someone has to remember. The plan's R9 explains why that matters: a prose document has no failing test.

**This gate covers what can be proven before the host exists.** A second gate covers the real host itself: the CLI's `verify` must pass against it before a patient account can be created (ADR-0022 item 4). Every row below is evidenced on a synthetic host or on paper. `verify` is what checks the host that will actually hold the data.

## How a row is signed off

- **The "Signed off" cell** holds `Name, YYYY-MM-DD` and nothing else. A row whose cell is `—`, empty, or in any other shape counts as **unsigned**.
- **What makes it a signature.** The cell format is not a signature. What makes it one is that the CLI reads the file from a tag signed in the operator environment. A sign-off typed in anywhere else is never what the CLI checks.
- **The sign-off rule.** The person signing confirms the evidence exists, and links it in the Evidence column. The signer must not be the person who did the work, wherever the project has a second person. Where it does not, say so in the Evidence column rather than leaving it implied. RD-5 and RD-12 in particular should carry a second reviewer wherever one can be found.
- **IDs are permanent.** They are never renumbered or reused, because issues, the ADR and the CLI's refusal message cite them.
- **Adding a row.** A new row arrives unsigned, so it re-closes the gate for any host not yet initialised. That is intended.
- **Removing a row.** This needs an ADR, or an amendment to ADR-0022, saying why the risk no longer applies. Do not delete one because it is inconvenient.

## What this list deliberately does not contain

- **Engineering completeness.** Missing features (P5–P8) are not readiness items. A patient can use what exists. What they must not get is guidance nobody ratified, a deletion that does not delete, or a diary protected by controls nobody has tested.
- **A BAA.** No BAA is legally required while the product is direct-to-patient (ADR-0017). The day a provider offers this app to their patients, HIPAA applies, and this list needs a BAA row and a formal risk-analysis row before anything else.
- **Checks on the real host.** Those are `verify`'s job (ADR-0022 item 4), because no row here can be evidenced on a host before it exists.
